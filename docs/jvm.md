# JVM mods (Java, Kotlin, Scala, ...)

A JVM mod is a jar. It uses the same `blockheads:api` as Luau and WASM mods, talks to the other mods through the same
services, custom events and channels, and is loaded by the same host. The difference that matters: **a JVM cannot be
sandboxed.** The mod runs with the permissions of the server or game process, so it must declare
`permissions.native = true` (players and server owners see the red *native* warning, and the owner has to grant
`native` in `mods.toml`). Use Luau or WASM when you can; use the JVM when you need a library or a language they do not
have.

| Host | JVM mods |
| --- | --- |
| Desktop server (`blockheads-server`) | Build with the `jvm` cargo feature (off by default) and set `BLOCKHEADS_JVM=1`; uses the JRE of the machine. |
| PC client (`blockheads-pc`) | Build the runner with the `jvm` feature (off by default); the launcher preference `mods_jvm` (runner flag `--mods-jvm`, `--mods-java-home`) turns it on; the user's JRE. |
| Android client | ART is already in the process. Loader built with `--jvm`, switched on by a `jvm-enabled` file; `classes.dex` inside the mod's jar, loaded with `InMemoryDexClassLoader`. |

## Quick start

```bash
bhmod new my-mod --lang java        # mod.toml, src/main/java/mod_my_mod/Main.java, build.sh, build.gradle.kts
cd my-mod
mkdir libs && cp /path/to/blockheads-mod-sdk.jar libs/    # attached to every mod-sdk release
./build.sh                          # javac + jar -> server/mod.jar   (or: gradle jar)
bhmod check . && bhmod pack .
```

`blockheads-mod-sdk.jar` holds the API (`club.blockheads.api.*`, generated from the WIT) and the helper classes
(`club.blockheads.mod.*`). Compile against it, do not bundle it: the host provides it at run time. Build for Java 8
(`--release 8`) so the same jar runs on every JRE and can be converted for Android.

```java
package club.example;

import club.blockheads.api.events.ChatEvent;
import club.blockheads.api.types.Priority;
import club.blockheads.mod.*;

public final class Main implements Mod {
    @Override
    public void onEnable(Api api) {
        api.onPlayerJoin(ev -> ev.player.sendChat("Hello, " + ev.player.alias() + "!"));

        api.onChat(Priority.LOWEST, false, (ChatEvent ev) -> {
            if (ev.text.contains("spam")) ev.cancelled = true;
        });

        api.command("hello", "Says hello.", (sender, label, args) ->
            Replies.reply("Hello, " + Senders.name(sender) + "!"));
    }
}
```

The jar manifest names the entry class: `Bhmod-Main: club.example.Main` (or `Main-Class`). The class needs a public
no-argument constructor and implements `club.blockheads.mod.Mod`. Nothing of the mod runs before `onEnable`.

`mod.toml`:

```toml
[entry]
server = { runtime = "jvm", path = "server/mod.jar" }

[permissions]
native = true
```

Kotlin and other JVM languages work the same way: the API is plain Java classes with public fields and lambdas.
(`ev.cancelled = true` is a field in Java; Kotlin sees the same field.) The Gradle template has a comment where to add
the Kotlin plugin. Examples in this repository: [`hello-java`](../examples/hello-java),
[`chat-filter-java`](../examples/chat-filter-java), [`scheduler-java`](../examples/scheduler-java) and
[`shop-java`](../examples/shop-java), which calls the `economy` service of the Luau economy mod.

## The API

The WIT interfaces become Java packages: interface `foo-bar` is `club.blockheads.api.foobar`. Everything in that
package is generated by [`scripts/gen-java.py`](../scripts/gen-java.py); the Javadoc comes from the WIT doc comments.

| WIT | Java |
| --- | --- |
| interface | Java interface (`Players`, `Storage`, ...) with the functions; the host-backed implementation is `PlayersImpl` etc. `Api` creates them: `api.players()`, `api.storage()`, `api.scheduler()`, ... |
| function `run-later` | method `runLater` |
| resource `player` | class `Player` with methods (`alias()`, `sendChat(text)`, `valueHandle()`, ...); equal when the id is equal |
| record | final class with public mutable fields and a constructor |
| enum | Java `enum` (`Priority.LOWEST`, `Role.MODERATOR`) |
| variant | abstract class with one nested class per case (`CommandSender.Console`, `CommandSender.Player` with a `value` field); `instanceof` to tell them apart |
| `option<T>` | `null` or the value |
| `result<T, E>` | returns `T`; throws an unchecked exception holding the error (`ApiErrorException.error`, `CallErrorException.error`) |
| `list<u8>` | `byte[]` |
| `list<T>` | `java.util.List<T>` |
| `u8`..`s32` | `int` |
| `u32`, `u64`, `s64` | `long` (`u64` is unsigned: use `Long.toUnsignedString`) |
| `f32`, `f64` | `float`, `double` |
| `types.value` (canonical CBOR) | a plain Java object, see below |

### Callbacks instead of the `guest` export

You do not implement `guest`; `Api` keeps the handlers:

| `guest` export | Java |
| --- | --- |
| `on-enable`, `on-disable` | `Mod.onEnable(Api)`, `Mod.onDisable()` |
| `handle-event` | `api.onChat(handler)`, `api.onPlayerJoin(...)`, one per built-in event kind (generated: `EventHandlers`), each also with `(Priority, ignoreCancelled, handler)`; `api.onCustom(name, handler)`; `api.off(id)`. The handler gets the event record and changes its fields in place: `ev.cancelled = true`, `ev.text = "..."`, `ev.amount = 0`, `ev.reason = RejectReason.BANNED`, `ev.payload = ...`. |
| `run-command` | `api.command(name, description, handler)` or `api.command(Spec.command("go").alias("g").minRole(Role.MODERATOR).build(), handler)`. The handler returns `Replies.reply("line", ...)`, `Replies.usage()` (not handled: the host shows the usage text) or `null` (handled, no reply). |
| `run-task` | `api.runLater(delay, task)`, `api.runEvery(delay, period, task)`, `api.runNextPoll(task)`, `api.cancel(id)` |
| `call-service` | `api.provide(name, version, (method, args) -> result)` |
| `on-channel-message` | `api.openChannel(name, (origin, data) -> ...)`, `api.send(channel, target, bytes)` |

Services from other mods: `api.service("economy", "^1").call("withdraw", player, 30L)`. Services on the other side
of the network (API 0.3.1): `api.callRemote(new RemoteTarget.Server(), "shop", "^1", "price", Arrays.asList("apple"),
3000L, new RemoteCallback() { ok(Object value) ... failed(String kind, String message) ... })` returns the call id at
once and the callback runs later; `api.cancelRemote(id)`; inside a provider `api.caller()` is the calling mod and
player. Raw access to any WIT import by
name, also one a newer host has and this SDK has no wrapper for yet: `api.bridge().call("interface.function", args...)`.

### Values (services, custom events, `storage` stays bytes)

`types.value` is canonical CBOR on the wire; in Java it is a plain object tree:

| Java | CBOR |
| --- | --- |
| `null` | null |
| `Boolean` | bool |
| `Long` / `Integer` / `Short` / `Byte` | integer (decoded as `Long`) |
| `Double` / `Float` | float (decoded as `Double`); a whole number you want as an integer must be a `Long` |
| `String` | text |
| `byte[]` | bytes |
| `List`, `Object[]` | list |
| `Map<String, ?>` | map (records use kebab-case keys) |
| `Player` | host handle `{"$h": n}`; decoding gives the player back, or throws `HostException("stale handle")` after they left |

Anything else, nesting deeper than 32 and values over 1 MiB throw `IllegalArgumentException("bad value: ...")`. A service
method can throw `ServiceError("message")` to answer with `provider-error` (not a fault); any other exception does the
same (like a Luau `error`), an `Error` (out of memory, stack overflow, assertion) counts as a fault of the provider.

## How the host runs it

- **One JVM per process**, created on first use from the user's JRE (`libjvm` is loaded at run time; nothing links
  against it). It is found through `BHMOD_JAVA_HOME`, `JAVA_HOME`, a runtime bundled with the app, or `java` on the
  `PATH`. Java 8 or newer. The embedded SDK jar is written to the system temp directory (or the configured work
  directory) and put on the class path. `-Xrs` is set so the JVM leaves the process' signal handlers alone, and the
  numeric locale is put back to `C` (the JVM changes it, which would make Luau read `0.2` as `0` in Turkish or German).
- **One class loader per mod**, a child of the loader that holds the SDK. A mod sees the SDK and the JDK, not other
  mods' classes; mods talk through services, events and channels like in every other language.
- **Everything runs on the game thread**, one call at a time. The API objects only work inside a call the host made; from
  another thread of your own they throw `IllegalStateException` ("the host API can only be used while the host runs
  the mod"). Do slow work on your own threads and hand the result back with `api.runNextPoll(...)` from a handler.
- **Budgets.** Soft 5 ms (a warning in the log), hard 25 ms. A JVM cannot be stopped from outside, so the hard
  deadline plus a grace period (250 ms; 5 s extra for `onEnable`, which loads your classes) wakes a watchdog that
  *interrupts* the thread: `Thread.sleep`, `wait`, blocking I/O end with `InterruptedException` and the call counts as
  a hard trap. A loop that never blocks cannot be stopped. Three traps in 60 s disable the mod, as for every runtime.
- **Faults.** An exception out of a handler is a fault (strike) and is logged with the first stack frames; an
  exception from `onEnable` disables the mod; an `Error` is a fault. A panic in the host while your code runs
  surfaces as an `IllegalStateException`.
- **Memory.** One heap limit for the whole JVM (`-Xmx`, 256 MiB by default; the per-mod `memory_bytes` of the other
  runtimes does not exist here).
- **Isolation.** None beyond class loaders. The mod can read files, open sockets, call `System.exit`... which is
  why it is `native`.

## Regenerating the bindings

The API classes under `sdk/java/src/club/blockheads/api` are generated from `wit/blockheads-api`:

```bash
scripts/gen-java.py            # rewrites them (Python 3, standard library only)
scripts/gen-java.py --check    # CI: fails if the committed files differ from the WIT
scripts/build-java.sh          # compiles the SDK jar and the example mods (needs a JDK)
```

Run it after every change to the WIT (a new interface gets its package, records, enums, variants, resources and a
host-backed class automatically; the rest of `club.blockheads.mod` is hand-written). A new *host function* also needs
its name in the Rust runtime (`call_host` in `crates/bhmod-core/src/jvm.rs`), and a new *event* in `event_value`; the
host answers an unknown function name with an exception, so a mod built against a newer SDK fails loudly on an older
host.

## Android (ART)

The loader already runs inside the game's process next to ART, so no JVM is started: the Rust side adopts the running
VM with `bhmod_core::jvm::attach_existing(java_vm, class_loader, config)`. Three pieces make it work:

1. **The loader build.** `scripts/build-android-loader.sh --jvm` builds `libbhmodloader.so` with the `jvm` feature of
   `bhmod-android` and puts the SDK classes (`sdk/java/src`) into the loader's own `classes.dex`, so the class loader
   of the loader's Java UI also finds `club.blockheads.*`. Without `--jvm` (the default) nothing of this is built.
2. **The switch.** JVM mods are unsandboxed, so the owner has to ask: the loader turns the runtime on (and puts `jvm`
   into `HELLO.runtimes`) only when the file `jvm-enabled` exists in its data folder. There is no UI toggle yet.
3. **The mod.** A jar for ART carries `classes.dex` next to its class files; the same jar still runs on a desktop JVM,
   which ignores the dex. Make it with the Android SDK's `d8` (the SDK jar is a classpath entry, not part of the dex):

   ```bash
   d8 --release --min-api 26 --lib $ANDROID_HOME/platforms/android-35/android.jar \
      --classpath blockheads-mod-sdk.jar --output dex-out $(find build/classes -name '*.class')
   (cd dex-out && zip ../server/mod.jar classes.dex)
   ```

   `ModLoader` finds `classes*.dex`, and `dalvik.system.InMemoryDexClassLoader` (Android 8, API 26), and loads the mod
   from memory: nothing is written to disk. On a device without it, or for a jar without a dex, it falls back to
   defining `.class` entries, which ART rejects with a clear error.

What is verified: `tests/android-art/run.sh` starts an x86_64 emulator (never a phone: everything is addressed by the
emulator's serial), puts the SDK dex and a Rust cdylib on `app_process`, adopts the VM and runs `hello-java`
(mod jar + `classes.dex`), event mutations, a service between two Java mods and the watchdog interrupt through the
real mod host, on Android 11. What is not: the game process on a real phone (Thumb game code, the loader's UI toggle,
memory with the game running, Android 14 behaviour) — see `notes/resume/m9-jvm.md`.

## Tests

`crates/bhmod-core/tests/jvm_conformance.rs` runs the Java twins of the three conformance examples against the Luau
ones through the real host and compares transcripts (like the WASM suite), plus `shop-java` calling the Luau economy.
`jvm_runtime.rs` covers every event, the whole API, mutations, services between Java mods, channels, interruption and
every way a mod can fail, with fixtures compiled from `tests/jvm-fixtures`. They need a JDK:

```bash
scripts/build-java.sh
cargo test -p bhmod-core --features jvm
```

## For host developers

`bhmod-core` with `features = ["jvm"]` (needs a JDK to build: `build.rs` compiles `sdk/java`). Add the runtime to
`HostOptions::runtimes` next to the others:

```rust
let rt = bhmod_core::jvm::JvmRuntime::new(bhmod_core::jvm::JvmConfig::default())?; // finds the JRE, starts the JVM
opts.runtimes.push(Box::new(rt));
```

Keep it opt-in (the server uses `BLOCKHEADS_JVM=1`). `JvmConfig` sets the JRE (`java_home`, `bundled`), heap, extra JVM
options, where the SDK jar is written and the grace periods. One JVM per process: the first configuration wins, and a
failed start is remembered. Scale `grace` with your budgets on slow machines. Call it from the game thread: the host API
is only usable inside the calls the host makes.
